# Deep audit — live database drift and silent failures

**Date:** 2026-07-28 · **Scope:** `basic website/` against the live Supabase
project `dyajmgddsiqcnlehqbhl` · **Method:** live PostgREST schema pulled and
diffed against every `.from()` / `.rpc()` reference in `lib/` and `app/`.

This closes an open question from `demo-to-production-inventory.md` §7, which
noted *"Live Supabase schema and data were not re-queried this session — verify
against the live project once access is restored."* It has now been queried.

---

## Headline

**57 of the 107 tables the application code reads or writes do not exist in the
live database.** So do 3 of its 4 stored procedures.

The prior assumption was that drift ran one way — that the repo's migrations
*omitted* things the live DB had (the `rsg_*` voice-agent subsystem). That is
true, but the more consequential drift runs the **other** way: the live database
is missing more than half of what the code depends on.

| | Count |
|---|---|
| Tables referenced by code | 107 |
| Missing from live DB | **57** |
| Code sites touching a missing table | **291** |
| …that propagate the error (visible failure) | 247 |
| …that swallow it (silent no-op) | **44** |
| RPCs referenced / missing | 4 / **3** |

The live database is legitimate and is the right one — it holds the `rsg_*`
voice/CRM subsystem and the `audit_*` subsystem with real data. The gap is real.

### What still works

The public revenue path is intact. `leads`, `clients`, `bookings`,
`booking_sessions`, `appointment_types`, `availability_*`, `notification_*`,
`proposals`, `qualification_*`, and the scheduling tables all exist. The
marketing site, contact form, chatbot lead capture, and booking flow are backed
by real tables.

### What does not

Every table behind these subsystems is absent: **client lifecycle**
(`lifecycle_proposals`, `contracts`, `contract_signatures`, `invoices`,
`payments`, `milestones`, `projects`, `project_tasks`, `renewals`),
**client portal** (`client_users`, `client_activity`, `tickets`, `files`,
`training_*`, `reports`, `requests`), **assessments/questionnaires**,
**Security Center** (`security_settings`, `security_incidents`,
`security_vendors`, `security_tests`, `retention_rules`, `ai_approvals`),
**audit log** (`audit_events`), **admin accounts** (`admins`,
`admin_sessions`), **AI metering** (`ai_usage`), and the **email retry queue**
(`email_jobs`).

## Findings, by severity

### H1 — AI spend is uncapped and unmetered in production

`lib/ai/usage.ts` — `ai_usage` does not exist live.

- `recordAiUsage()` catches the insert failure and logs. **No usage is recorded
  at all**, so per-tenant AI cost attribution is entirely empty.
- `isTenantOverAiCap()` **fails open** — it returns `false` when usage cannot be
  read, so `MONTHLY_TOKEN_CAP` (default 5M tokens/tenant/month) **can never
  trigger**.

Failing open is the right call for a *transient* metering outage, which is what
the code comment describes. Here the condition is permanent, so a deliberate
graceful-degradation choice has silently become "there is no cap." Nothing
surfaces this.

**Fix:** create `ai_usage` (already defined in
`20260727120000_ai_usage.sql`, never applied).

### H2 — There is no audit trail

`lib/audit.ts` — `audit_events` does not exist live.

`writeAuditEvent()` catches and `console.warn`s, so **every** admin action,
auth event, and cron run writes nothing. `listAuditEvents()` returns `[]` and the
admin UI renders an empty audit log that is indistinguishable from "no activity."
For a business selling security and compliance consulting, an audit log that
looks populated-but-empty is worse than an absent feature.

**Fix:** create `audit_events` (defined in
`20260715180000_enterprise_hardening.sql`, never applied).

### H3 — Failed lead-notification emails are dropped *(reported earlier)*

`lib/leads.ts` → `lib/email-jobs.ts` — `email_jobs` does not exist live.

When a lead notification fails its first send, the code falls back to the
durable retry queue. `enqueueEmailJob()` catches the missing-table error and
returns `false`, so the lead's notification is discarded with one
`console.warn`. Same root cause: defined in
`20260715180000_enterprise_hardening.sql`, never applied.

### M1 — The Security Center reads defaults and reports them as configuration

`lib/security-center/store.ts` — `security_settings` does not exist live.

`getSecuritySettings()` falls back to `DEFAULT_SECURITY_SETTINGS` on failure and
caches them. Consequences: the **AI kill-switch** (`aiPaused`) always reads
false, and **MFA enforcement** (`mfaRequiredRoles`) reads the default set. The
Security Center UI displays these defaults as though they were saved settings.

Mitigating: `updateSecuritySettings()` **fails loudly** — `writeFileStore()`
explicitly refuses to write in production, so an admin attempting to save gets a
real error rather than a false success. The feature is unavailable rather than
fake; the read-side silence is what makes it look configured.

### M2 — 44 access sites fail silently

The swallow pattern (`catch { console.warn(...); return [] }`) is concentrated in
`connect_links` (4/4 sites), `ai_approvals` (4/4), `private_ai_opportunities`
(3/3), `security_incidents` (3/3), `security_vendors` (2/2), `retention_rules`
(2/2), `security_tests` (2/2), `industry_verticals` (3/4).

These render as empty lists. The remaining 247 sites propagate their error and
surface as a failed request — noisy, but honest.

### L1 — `admins` / `admin_sessions` missing, but login still works

`resolveAdminContext()` → `getAdminById()` resolves the **env bootstrap owner**
(`ADMIN_EMAIL` / `ADMIN_PASSWORD`) as well as DB rows, so admin access survives.
DB-backed admin accounts, roles beyond the bootstrap owner, and server-side
session revocation do not. Worth knowing before adding a second admin.

## Instrumentation review (this session's changes)

Three defects found and fixed in my own work:

1. **Double-write.** `after(persist(record))` invoked `persist` eagerly, so the
   non-request-scope fallback (`await persist(record)`) ran it a second time —
   every call logged twice from cron and scripts. Now the promise is created
   once.
2. **Lost Anthropic request ids.** The SDK sets `_request_id` **non-enumerably**
   on successful responses; the lookup only checked `request_id`. Successful AI
   calls were recording `null` for the exact field Anthropic support asks for
   first. Fixed and covered by a test.
3. **FK could discard whole log rows.** `integration_runs.tenant_id` is a
   foreign key to `clients(id)`. Any caller passing a non-uuid tenant (a slug, a
   stale id from Stripe metadata) would have failed the insert and lost the
   entire record — silently, precisely when it mattered. Now the attribution is
   dropped and the row is kept.

Also fixed: **two uninstrumented Anthropic call sites** I had missed —
`app/api/chat/route.ts` (the public chatbot, the highest-volume AI path in the
app) and `app/api/admin/brief/route.ts`. Both now record.

Cost note: instrumentation cost 3 DB round-trips per provider call; the success
path now takes 1 (a success always resets the failure counter, so it needs no
read). Writes happen after the response via `after()`, off the user's latency
path.

### Pre-existing issue found while instrumenting

`app/api/chat/route.ts` constructs `new Anthropic()` directly rather than going
through `lib/ai/proxy`. It therefore bypasses the proxy's **kill-switch**,
**per-tenant rate limiting**, and **usage metering**. It has its own IP rate
limit, so this is not unbounded — but the public chatbot is the one AI surface an
anonymous visitor can drive, and it is the one not behind the central controls.

## Recommended order

1. **Apply `supabase/APPLY-integration-observability.sql`** to
   `dyajmgddsiqcnlehqbhl` — creates `email_jobs` (H3) and the observability
   tables.
2. **Apply the two never-applied migrations** for `ai_usage` (H1) and
   `audit_events` (H2). Both already exist in `supabase/migrations/`.
3. **Decide the fate of the lifecycle/portal subsystem.** ~50 tables and 291
   code sites are dead against the live DB. Either restore the schema from
   `supabase/backup-2026-07-27/` or accept those features as not-shipped and gate
   them in the UI. Leaving them reachable means admins click into features that
   500 or silently show nothing.
4. **Route the chatbot through `lib/ai/proxy`** so one kill-switch covers every
   AI path.

**Do not rebuild the schema from `supabase/migrations/`** — that folder does not
reproduce the live database in either direction. Use the captured backup.

## Method notes / limits

- Table existence was determined from the live PostgREST OpenAPI schema, which
  lists what the API can reach. A table existing but with different **columns**
  than the code expects would not be caught here — only presence was checked.
- `.from()` references were extracted by static pattern match; any table name
  built dynamically at runtime would be missed.
- Whether production Vercel points at `dyajmgddsiqcnlehqbhl` was confirmed
  verbally, not read from the Vercel environment. Worth verifying directly.
- Column-level and RLS-policy drift was not audited.
